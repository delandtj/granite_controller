# plane-fw

**Attic (2026-11-10):** the rev D plane binary with the I2C link, frozen.
The CAN FD plane core gets its own FD-only binary in firmware/ (firmware
ADR 0005 decision 9 as amended); this crate stays buildable as the
reference for the board glue.

The plane core application for the **STM32G070CBT6** on the PP-48 core
board (rev D): embassy on thumbv6m, with all of the behaviour in the
workspace crate [`plane-logic`](../../../firmware/plane-logic) and nothing but board
glue here.

- Design: `firmware/docs/adr/0002-plane-core-firmware.md`
- Link protocol: `firmware/docs/adr/0003-plane-link-protocol.md`
- Pins: `attic/firmware/plane-core-pins.toml` (generated by
  power/pp-48/tools/gensch.py core; the truth)
- Press deadline: `docs/press-deadline-line.md`
- CAN FD generation: `firmware/docs/adr/0005-plane-link-can-fd-transport.md`
  decision 9 (a separate FD-only binary, not features of this one)

This crate is **not in the firmware/ workspace**: it has its own
target, linker script, toolchain file and `.cargo/config.toml`, and
takes granite-proto and plane-logic by path from firmware/.

## Build

```sh
cd attic/firmware/plane-fw
rustup target add thumbv6m-none-eabi     # once
cargo build --release
cargo clippy --release -- -D warnings
```

`rust-toolchain.toml` pins stable with the target and `llvm-tools`.
`build.rs` parses `../plane-core-pins.toml` and the `core_pins!` table
in `src/pins.rs` and fails the build when a net moved port, changed
mode, or is missing from the firmware's map: there is no test harness on
the board, so that check is the pin map's test.

## Flash and watch (SWD on PA13 / PA14)

```sh
cargo run --release                      # = probe-rs run --chip STM32G070CBTx
probe-rs attach --chip STM32G070CBTx target/thumbv6m-none-eabi/release/plane-fw
```

The runner is in `.cargo/config.toml`; `DEFMT_LOG=info` is set there
too, so `trace`/`debug` calls are compiled out of the image. Logs come
over RTT (defmt).

## Size

`llvm-size` of the release image, against the ~52 KB ACTIVE slot of ADR
0002 decision 2 (and the ~56 KB a slot would be if BOOT shrinks):

| Section | Bytes |
|---|---|
| `.vector_table` | 184 |
| `.text` | 39 620 |
| `.rodata` | 6 928 |
| `.data` | 80 |
| **flash total** | **46 812 (45.7 KB)** |
| RAM (`.data` + `.bss` + `.uninit`) | 7 740 of 36 KB |

So the A/B swap of ADR 0002 decision 9 still fits, and the "copy-only
update above ~48 KB" fallback is not needed yet - but there is only
about 5 KB of headroom before it is. `opt-level = "z"`, fat LTO, one
codegen unit; debug info stays in the ELF (it is not loaded) because
probe-rs and defmt-decoder need it.

## What runs

- **Clocks**: 8 MHz HSE crystal (`hse_hz` in the pin map) -> PLL
  M=1 N=16 R=2 -> 64 MHz SYSCLK. The HSI stays on as the ADC clock: the
  G0's ADC takes at most 35 MHz.
- **Link task** (`src/link.rs`): I2C1 (PB8 / PB9, AF6) as an I2C slave
  at `0x30 + ADR[2:0]` (PA15 / PD1 / PA8, pulled up, DIP closed = 0).
  A 2-byte write is a read request and is answered out of the model on
  the spot (`Plane::handle_frame`); the answer is clocked out on the
  read that follows the repeated start and kept afterwards, so a retried
  read gets the same snapshot. A 4+ byte write is a frame, CRC-checked
  and queued for the bus task. embassy-stm32 0.6's own slave support is
  used (`into_slave_multimaster`, `listen`, `respond_to_write`,
  `respond_to_read`, including repeated-start detection): the ADR's
  PAC-level fallback was not needed.
- **Bus task** (`src/main.rs`, `src/segment_bus.rs`): I2C2 (PA11 /
  PA12, AF6) at 100 kHz as `plane_logic::SegmentBus` - blocking
  transfers, because this task is the only owner of the bus. It calls
  `Plane::tick` every 10 ms; the poll cycle inside it is scheduled at
  50 ms (ADR 0002 decision 5) and the finer tick only buys resolution
  for the sequences and the PRESS_TRIG toggling. It also feeds the
  500 ms IWDG, but only when `Plane::may_feed_watchdog` says a full
  cycle ran, and resets the board when the plane asks.
- **Status task** (`src/status.rs`): LED_RUN (PB14) 1 Hz heartbeat,
  5 Hz while an update runs, double blink while unconfirmed; INT_OUT
  (PD2) high while unacknowledged events exist. Both from two atomics
  the other tasks publish, so the heartbeat cannot be stalled by a poll
  cycle holding the plane.
- **Press deadline**: PRESS_TRIG (PB12) is toggled by the plane logic
  from the task that owns the press, about every 200 ms, and never
  otherwise - no timer, no DMA, so a hung firmware loses PRESS_EN after
  about a second.
- **MUX_RST** (PB13) and **EXP_RSTN** (PD0, open drain) are the two
  recovery lines; `unstick` drives nine SCL clocks on PA11 with I2C2
  disabled (through the PAC) before the mux reset.
- **VIN_SNS** (PB11, ADC_IN15): 220k / 10k divider, integer conversion
  to the wire's 10 mV units, read on every tick.
- **TAMP backup registers** (`src/backup_regs.rs`): the intended state
  of ADR 0002 decision 3. embassy-stm32's RTC backup-register accessors
  are stubs on this family (the words are in TAMP, not RTC), so this
  goes through the PAC after enabling the RTC/TAMP APB clock and
  clearing the backup-domain write protection.
- **CONFIG pages** (`src/config_store.rs`): the two copies with a
  sequence number and a CRC-32, in the **last two flash pages**
  (0x0801F000 / 0x0801F800) for now - see below.

Panics use `panic-probe` with `print-defmt`: the location is printed
over RTT and the core stops, which on a board in the field means the
IWDG resets it and the new image releases every press on its way up
(ADR 0002 decision 3). `panic-halt` would have cost the message and
gained nothing.

## What is stubbed or deliberately different

- **Firmware update over the link** (`src/update_store.rs`,
  ADR 0002 decision 9): every DFU operation refuses with a storage
  error, so FW_BEGIN fails and the controller reads update state
  "failed". There is no `plane-boot` and no partition split yet, and a
  DFU write with this `memory.x` would land in the running image.
  Needs: plane-boot (embassy-boot-stm32, IWDG fed through the swap),
  the memory.x split of decision 2, and `FirmwareUpdater` behind the
  six methods of `UpdateStore`.
- **`memory.x` takes the whole 128 KB** and the image is flashed at
  0x08000000 over SWD. The slot plan (16 KB BOOT / 2 KB STATE / 4 KB
  CONFIG / 52 KB ACTIVE / 54 KB DFU) is written out in `memory.x` as
  the comment it will become. embassy-stm32's `memory-x` feature is
  **off** on purpose: this file is the one that carries the slot plan,
  and two memory.x on the linker's search path would be a coin toss.
- **CONFIG pages are at the end of flash**, not at 0x08004800. They
  move with the bootloader; the first boot after the move reads blank
  pages, falls back to the defaults and the controller re-writes the
  set (it compares the config hash in INFO).
- **MCU temperature** (STATUS 0x11) reports nothing: the G0 sensor
  needs the two factory calibration words and a division per sample,
  and no plane decision depends on it (the unit hot-swap latch judges
  the *core input voltage*, which is read).
- **The IWDG starts after `Plane::boot`**, not before it. A
  four-channel discovery scan with NAK timeouts can outlast 500 ms, and
  what bounds a held button during boot is the hardware press deadline:
  PRESS_TRIG is not toggled until a press runs, so PRESS_EN is already
  dead when the application starts.
- **A link write longer than 255 bytes is truncated** and then fails
  its length check (counted in STATUS 0x19). The slave sets its
  transfer up in chunks below 256 bytes; the longest frame ADR 0003
  defines is a FW data record at ~137 bytes.
- **The plane is behind one mutex.** Neither task awaits while holding
  it, so they cannot interleave inside the state machine, but a read
  request that arrives mid-poll-cycle stretches the clock until the
  cycle ends (a few ms, up to ~25 ms at four units). ADR 0002 decision
  8 wants stretching to be a fallback: measure it on the bench with the
  ISO1640 in the path, and if the controller minds, cut the cycle into
  per-unit steps that release the mutex between units.
- **CAN FD** (ADR 0005 decision 9) is not here. The transports become
  features of this binary; nothing in the structure above assumes I2C
  past `src/link.rs`.

## Untested

Nothing in this crate has run on hardware: there is no core board here.
What is verified is `cargo build --release` and
`cargo clippy --release -- -D warnings` for thumbv6m-none-eabi, the pin
map against the generated TOML, and the behaviour underneath - which is
`plane-logic`'s host test suite over its simulated devices. Everything
that only exists on the board is unproven: the 64 MHz PLL bring-up, the
I2C slave against a real master through the ISO1640 (clock stretching,
the repeated start, the lost-byte question ADR 0002 lists as a risk),
the ADC scaling of the divider, the TAMP words surviving a reset, the
flash CONFIG pages, the nine-clock recovery, and the press deadline
monostable being retriggered often enough.

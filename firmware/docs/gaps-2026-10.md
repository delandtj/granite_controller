# Firmware gaps found while documenting the controller (2026-10-10)

Brief for whoever picks these up. Each item is self-contained: what an
operator sees, where it is in the source, what the design (ADR 0001,
`firmware/docs/adr/0001-firmware-architecture.md`) intended, a fix
outline and how to prove it. Line numbers are from branch
`eight-node-expander` at commit db9363d; re-grep before editing.

Context: the firmware is Rust on ESP-IDF in `firmware/granite-fw`
(board binary, standalone crate) over `firmware/granite-core` (host-
tested core: actuator, rules, config, dispatcher, API handlers).
`firmware/granite-sim` runs the core on the host. `firmware/README.md`
has build, flash and test instructions. All of this was found by
reading the code; no rev C board has been powered yet. Items are ordered
by operator impact. Keep `cargo test` in `firmware/` green and
`cargo clippy --release --all-targets -- -D warnings` clean in
`firmware/granite-fw`.

The documentation site (`site/`, mdBook) carries a "Current firmware"
note for every item below; remove the note when the item is fixed.

---

## 1. Per-node boot policy is never applied on the board

Symptom: `nodes.nodes[i].boot_policy = "on"` is stored, shown on the
Nodes page, and does nothing after a controller boot.

Where:
- `granite-core/src/actuator.rs:808` `Actuator::submit_boot_policy`
  exists and is tested.
- `granite-core/src/config.rs:275` `NodesCfg::boot_policies()`.
- The only caller is `granite-sim/src/sim.rs:159-164`. Nothing in
  `granite-fw/src` references `submit_boot_policy`, `boot_policies` or
  `t_settle_ms`.

Intended (ADR component 3, "boot policy"): once per controller boot,
`t_settle_ms` (default 5 s) after the expanders are up, submit the
policies through the actuator so `on` nodes come up in `nodes.order`
with `t_stagger_ms` between presses and `leave` nodes are untouched.
A hardware layer that failed to initialise must not run it.

Fix outline: in `granite-fw/src/main.rs`, in the dispatcher thread
(the loop that owns `actuator` and calls `rules.tick`, around line
500-530), add a one-shot: when `hw_ok` and `now >= boot_ms +
t_settle_ms` and not yet done, read `platform.config().nodes
.boot_policies()`, call `actuator.submit_boot_policy("boot", ...)`,
append the returned events like the rule path does. Log one line with
the policies that were submitted. Mirror the simulator at
`sim.rs:159-168`.

Acceptance: on a devboard with `--features hwtest` expanders absent the
policy must not run (log says so). On the simulator (`cargo run -p
granite-sim -- serve`) it already runs; on the board, with one node
set to `on`, a controller reboot produces `accepted` + `action_done`
events for `node N action on id boot` and a PWR press on the right
channel (hwtest or a LED on the relay output).

## 2. Target `all` is refused for every action except `on_all`

Symptom: `POST /api/v1/nodes/all/force_off`, the MQTT command
`{"action":"force_off","target":"all"}` and the shipped default rules
(`force_off` on `all`) are refused with `bad_target`. The three
default rules at `granite-core/src/rules.rs:389-435` therefore fire,
publish `rule_fired`, and do nothing.

Where: `granite-core/src/actuator.rs:795-797`:
```
let Some(node) = req.target.node() else {
    // Every other action needs exactly one node.
    return Submission::Done(ActionResult::refused(RefuseReason::BadTarget));
};
```
`on_all` is handled just above it through `submit_group`.
`granite-fw/src/main.rs:521-527` submits a fired rule's action and
discards the `Submission` (the refusal only shows as an
`action_failed`-style event in `evs`, if at all).

Intended (ADR component 3: "Node ids are 1-8 or all"; component 5:
default rule "force_off all"). ADR component 3 also fixes "one
physical press at a time overall", so `all` must serialise, not
parallelise.

Fix outline: in `submit`, when `req.target` is `All` and the kind is
`On`, `Off`, `ForceOff`, `Reset` or `Cycle`, build the target list
from `self.order` (for `Off`/`ForceOff`/`Reset` only nodes whose LED
is `Some(true)`; for `On` the current `on_all` filter; for `Cycle`
every node) and call `submit_group(req, kind, &targets, ...)` the way
`OnAll` does. `Press` with `all` stays refused (raw presses are
per-node by design). Keep the group semantics: one `accepted`, one
`action_done`/`action_failed` per child, `partial` on the parent when
any child fails. Decide whether a group `ForceOff` should use
`t_stagger_ms` between children (it should not: a leak or over-temp
wants every node off as fast as the one-press-at-a-time rule allows,
so use 0 stagger for `Off`/`ForceOff`/`Reset`, `t_stagger_ms` for
`On`/`Cycle`).

Acceptance: new tests in `actuator.rs` next to the `on_all` ones:
`force_off all` with three nodes on presses three times in order and
acks once; `reset all` skips off nodes; `press all` is still
`bad_target`. The default rules test in `rules.rs` plus an actuator
submit must produce presses. `cargo test` in `firmware/`.

## 3. HTTP node actions reply `accepted` at queue time; failures are invisible to HTTP

Symptom: `POST /api/v1/nodes/3/on` returns 200 `{"result":"accepted"}`
immediately. A later `power_on_timeout` only appears as an
`action_failed` event (MQTT) and in `state.nodes[2].last_action`.
`firmware/README.md` and the setup page's buttons assume the reply is
the outcome.

Where: `granite-fw/src/main.rs:439` `reply.send(out.reply.clone())`
right after `dispatch`; `granite-core/src/dispatch.rs:105`
`Submission::Accepted { .. } => Reply::accepted(&cmd.id)`. The MQTT
path gets its completion ack from the actuator events (`msg.rs`), so
MQTT is correct and HTTP is not.

Intended (ADR component 8: `/api/v1` "carries the same command
vocabulary as MQTT"; component 7: ack "published when the action
completes").

Fix outline, pick one:
- (a) Document it: keep `accepted`, and make the setup page poll
  `state` for `last_action` of that node (the page already refreshes
  status). Cheapest, and the honest reading of a queue.
- (b) Make HTTP wait: in the dispatcher, for `Submission::Accepted`
  from a node action, hold the `reply` sender in a map keyed by
  command id and send the final `Reply` when the matching
  `ActionDone`/`ActionFailed` event arrives (the same place the MQTT
  ack is produced), with a cap (`t_soft_off_ms + t_hold_ms + margin`)
  and a 202 fallback if the HTTP server's own timeout is shorter.
  esp-idf-svc's HTTP handler runs on the server task, so holding it
  for two minutes blocks that task; check `CONFIG_HTTPD_MAX_REQ_HDR
  _LEN` / session timeouts before choosing (b).
Recommendation: (a) now, plus a `?wait=1` query parameter doing (b)
with a 30 s cap for scripts, if cheap.

Acceptance: `granite-sim` with a node `respond = "never"`:
`POST /nodes/1/on` and `GET /state` shows `last_action.result =
"failed: power_on_timeout"` after `t_on_ms`; with `?wait=1` the POST
itself returns that.

## 4. Staged `mqtt` and `sec` sections are not applied live and have no revert

Symptom: enabling MQTT from the page stages the section; nothing
connects until confirm *and* a reboot. The status page shows
`staged.seconds_left` counting down, but when it reaches zero nothing
happens: the staged value just sits until confirm or revert. The MQTT
page's "auto-confirm on connect" box does nothing.

Where:
- `granite-fw/src/platform/api_impl.rs:278-291`: only `net` goes to
  `platform.net.apply`; other sections log "takes effect on confirm
  plus a reboot". `deadline_ms` is set (`:291`) and only reported.
- `granite-fw/src/main.rs:598-614`: same, with the TODO.
- `granite-fw/src/mqtt.rs:700-708`: the worker notices a changed
  section every `CONFIG_REFRESH` and logs "applied on the next
  restart".
- `granite-fw/src/main.rs:268`: the worker thread is only started if
  `mqtt.enabled` at boot.
- `granite-fw/src/platform/net.rs:360-376`: the revert-and-reboot
  timer exists for `net` only.

Intended (ADR component 6, commit-confirm): "For MQTT broker changes,
confirm means the new broker connects and the client confirms, or
auto-confirm if auto_confirm_on_connect is ticked." Unconfirmed staged
changes revert at the deadline. ADR component 8: a new device
certificate is picked up by the HTTPS server.

Fix outline:
- MQTT: always start the worker thread (it already idles when
  disabled: `main.rs:257` comment). Give it a `reconfigure` path:
  when the *live* section (staged or stored) differs in
  `connection_differs`, tear down the client and rebuild with the new
  settings. Feed it the staged section through the same
  `Arc<RwLock<Config>>` the dispatcher uses (`ctx.config` is already
  updated at PUT time, see item 10 note), so no new plumbing.
- Deadline: one timer for all staged sections. For `net` keep the
  reboot. For `mqtt`/`sec` on timeout: restore the stored section into
  the live config and reconfigure (no reboot needed).
- `auto_confirm_on_connect`: when the worker reaches `connected` while
  `mqtt` is staged and the flag is set, call the same `confirm` the API
  uses (promote all staged sections, or only `mqtt`; the ADR says the
  broker change, so only `mqtt`).
- HTTPS certificate reload: esp-idf-svc's `EspHttpServer` cannot swap
  its TLS config in place; a reboot is acceptable here. Make the page
  say so (`web/app.js:660` currently says "reconnect").

Acceptance: on a devboard with `--features wifi-dev` and
`tools/mqtt-smoke.sh`: PUT `mqtt` with the broker enabled -> within
`CONFIG_REFRESH` the broker sees `status` -> wait past `t_confirm_s`
without confirming -> the session drops and the stored (disabled)
config is back, no reboot. With `auto_confirm_on_connect` the section
is promoted and survives a reboot.

## 5. Static dead-man counts only gateway pings; accepted connections never reset it

Symptom: a static configuration with an empty `gateway`, or a gateway
that drops ICMP, falls to DHCP after `t_deadman_s` (default 1 h) even
while an operator is logged in over HTTPS.

Where: `granite-fw/src/platform/net.rs:488-540`. The loop reads
`LAST_CONN_S`, which `note_connection()` (`net.rs:181`) sets, but
`grep -rn note_connection granite-fw/src` finds no caller: neither
`http.rs` nor `modbus.rs` nor `mqtt.rs` calls it. Also, per the TODO
at `net.rs:525-531`, DHCP replaces the static address instead of
running alongside it.

Intended (ADR component 6): "no gateway ARP reply **and** no accepted
TCP connection for t_deadman"; DHCP alongside without dropping the
static address.

Fix outline: call `net::note_connection()` from the HTTPS request
path (`http.rs`, where the handler is entered; one call per request is
fine), from the Modbus accept loop (`modbus.rs`) and from the MQTT
worker on a successful connect (a broker session is also proof of
reachability). Treat an empty `gateway` as "no probe possible": do not
arm the dead-man unless `gateway` is set, and log that once at boot.
Leave the "alongside" TODO; document that DHCP replaces the static
address.

Acceptance: devboard with `wifi-dev`, static config, `t_deadman_s =
120`, gateway set to an address that does not answer: with a browser
polling the status page the dead-man must not fire; without it, it
fires at 120 s and `net` shows `deadman fired`. `gateway = ""`: never
fires, boot log says why.

## 6. Fault bits 2, 3 and 5 are never set; bit 0 only at init

Symptom: Modbus input register 13 and the fault word in `status` never
show `probe_missing`, `vin` or `config_fallback`, and a runtime press
deadline or expander readback mismatch does not set `expander` (bit 0).

Where: `granite-core/src/modbus_map.rs:56-68` defines the seven bits
and `docs/modbus_map.md` documents them. Writers in `granite-fw/src/
main.rs`: `:228` (EXPANDER|SENSE at hardware init failure), `:758-760`
(SENSE from the sense thread), `:826-833` (MQTT_DOWN, OTA_PENDING).
Nothing writes PROBE_MISSING, VIN or CONFIG_FALLBACK; the actuator's
`Fault` events (`press_deadline`, `expander`) are published but do not
touch the word.

Intended (ADR component 9 register map; component 4 "a missing probe
is reported"): the word mirrors the current fault state.

Fix outline, in `main.rs`:
- PROBE_MISSING: in the sense thread after each probe cycle, set when
  any *configured* probe (`nodes.probes`) returned `None`, clear
  otherwise.
- VIN: define the window. Nothing in `config.rs` has one; add
  `nodes.vin_min_mv` / `nodes.vin_max_mv` (defaults 16000 / 22000, 0
  = unchecked) with validation and a line on the Nodes page, or derive
  from the default rule 3 threshold. Set/clear in the sense thread.
- CONFIG_FALLBACK: set at boot when `Config::load` reported any
  `SectionFallback` (the dispatcher already emits the `config`/
  `fallback` event there); it stays set until the section is written.
- EXPANDER at runtime: where the dispatcher handles actuator events,
  set on `Fault { press_deadline | expander }`, clear after the next
  successful expander readback (the 1 s verify in the hardware layer
  already knows).

Acceptance: `hwtest` with no probe configured -> bit 2 clear; with a
ROM configured and absent -> set. Simulator cannot test the word
(Modbus is core-only there), so this is a devboard/board check through
`status` on the console and the register.

## 7. OTA `started` and `downloading` events are never emitted

Symptom: a pull update produces no progress; the first event is
`verified` or `failed`.

Where: `granite-fw/src/platform/ota.rs:323,342,348,365` emit
`pending_verify`, `valid`, `failed`, `rolled_back`; `main.rs:634,649`
and `api.rs:1715,1731` emit `verified`/`failed`. `msg.rs` documents
`started` and `downloading` with a `progress` percentage.

Fix outline: in `ota::pull` emit `started` before the first byte and
`downloading` every 10 % (Content-Length known) or every 256 KiB; in
the HTTP upload sink (`api.rs` firmware/upload) emit the same from the
chunk loop. Progress goes to the `event` topic and the Firmware page
already has a progress bar for the push case.

Acceptance: `mosquitto_sub -t 'granite/#'` during a pull shows
`started`, several `downloading`, `verified`, then after the reboot
`pending_verify` and `valid`.

## 8. `mqtt.skip_time_check` is accepted and ignored

Where: `granite-fw/src/mqtt.rs:481-485` logs that esp-mqtt has no such
option. The MQTT page and `config.rs` still expose it.

Fix outline: either remove the field from `config.rs` (schema stays 1
if `#[serde(default)]` tolerates its absence; unknown fields are
ignored on import) and from `web/index.html`/`app.js`, or implement it
with `esp_mqtt_client_config_t.broker.verification.skip_cert_common
_name_check`-style option if a time-check skip exists in the ESP-IDF
version in use (v5.5.5: check `esp_tls_cfg_t`; there is no
not-before skip in esp-tls, so removal is the honest option).

## 9. `vin_trim`, probe names and `t_probe_s` are read once at boot

Where: `granite-fw/src/main.rs:157` reads `vin_trim` into the hardware
layer at init; the sense thread (`main.rs:678-711`) takes `probes` and
the period at start. `apply_config` (`main.rs:545`) re-applies only
timings, order, sense mode and rules.

Fix outline: extend `apply_config` (it already runs on every `nodes`
save) to push `vin_trim` into the VIN reader (an `AtomicU32` of the
trim in milli-units is enough), the probe name map into the sense
thread's shared state, and `t_probe_s` into the loop's sleep. Add to
the Nodes page text that these apply immediately once done.

Acceptance: change `vin_trim` on the page; `vin_v` on the next status
refresh reflects it without a reboot.

## 10. Console `set-password` invalidates every API token

Where: `granite-fw/src/platform/mod.rs:388-396` `set_admin_password`
mints a fresh salt and overwrites `secrets.admin_salt`. API tokens are
PBKDF2-hashed with that same salt; the API path (`granite-core/src/
api.rs:1789`) deliberately keeps the salt for that reason.

Fix outline: in `set_admin_password`, reuse `secrets.admin_salt` when
it is non-empty, mint only when empty. Then the console and API paths
agree.

Acceptance: create a token over the API, `set-password x` on the
console, the token still authenticates.

Note on item 4: `put_section` in `api.rs` (~1583) writes the validated
section into the live `ctx.config` at PUT time; that is how the
`config-watch` thread starts the Modbus listener before confirm. Keep
that behaviour in mind when wiring the revert in item 4: revert must
restore `ctx.config` from the store, not just drop the staged list.

## 11. Factory reset erases the device certificate; the page says it survives

Where: `granite-fw/src/platform/store.rs:9-10`: `secrets` (which holds
the device key and cert) is erased by a factory reset; only `factory`
(recovery token, fleet key) is kept. `web/index.html:296-297` says
"the recovery token and the device certificate survive".

Fix outline: either move `device_key_pem`/`device_cert_pem` to the
`factory` namespace (ADR component 10 says "device cert if kept", so
this was the intent: a stable fingerprint across resets is useful for
pinning), or correct the page text. Moving them means `identity.rs`
loads from `factory` and the Security page's "upload certificate"
writes there too.

## 12. The recovery-token "shown once" flag makes the page skip the token after a console `set-password` or a factory reset

Where: `granite-fw/src/platform/api_impl.rs:36-37,159-171`: the flag
`rtokshown` lives in the `factory` namespace, so it survives a factory
reset; after a reset the first-setup page gets `recovery_token: null`.
Setting the password from the console never shows it at all (by
design, the console prints it), which is fine.

Fix outline: clear `rtokshown` in `Store::factory_reset`, so the
first setup after a reset shows the token again (it is unchanged, but
the person doing the reset may not be the one who recorded it).

## 13. No HEAD handlers in the HTTPS server

Where: `granite-fw/src/http.rs:318-321` registers Get, Post, Put,
Delete; the core route table (`api.rs`) handles `HEAD` for every GET.
Harmless; add `HttpMethod::Head` to the list if a monitoring tool
wants it.

## 14. No documented way to produce the OTA `.bin`

`firmware/README.md` covers flashing the ELF with espflash and
uploading "a `.bin`" but never says how to make one. `espflash
save-image --chip esp32c6 <elf> <out.bin>` produces an application
image; for a build with `sdkconfig.defaults.signing` the image must
carry the signature block, so the step is `espsecure.py sign_data
--version 2 --keyfile signing_key.pem --output signed.bin out.bin`
(or confirm that the ESP-IDF build's `.bin` under `target/.../build/`
is already signed and use that). Verify once by pushing to a bench
board, then write it into the README "OTA, signing and probation"
section and into `site/src/reference/building.md`.

## Not gaps, but worth knowing

- `probe_scan` is accepted and not wired to the 1-wire bus
  (`main.rs:661`, TODO). Probes are enumerated at boot only.
- VLAN tagging is not implemented (`net.rs` ~701); the Network page
  still shows the field.
- The simulator does not model items 1-4 the way the board does: it
  *does* apply the boot policy and it has no MQTT worker, so a fix
  must be checked on the board or on a `wifi-dev` devboard.
- `docs/handoff.md` has the bring-up order and the devboard features.
